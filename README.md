# Ответы на задание

## 1. Архитектура решения

Запрос «Проанализируй работу отдела продаж за последние 30 дней» запускает конвейер из трёх ролей. В этом проекте это программные модули с явными шагами; отдельные автономные LLM-агенты для загрузки и расчётов не нужны.

**Координатор** — [CLI и сервер](auditor/__main__.py). Он выбирает период, фиксирует время среза и собирает источники. [Коннектор amoCRM](auditor/amo.py) читает сделки и задачи через `GET /api/v4/leads` и `GET /api/v4/tasks`, а также пользователей, воронки и компании через `GET /api/v4/users`, `GET /api/v4/leads/pipelines` и `GET /api/v4/companies`. Авторизация — Bearer-токен, полученный для аккаунта; коннектор проходит страницы и повторяет временные ошибки API. Первичная выдача и обновление OAuth-токенов выполняются вне проекта.

**Аналитик звонков** — [адаптер телефонии](auditor/telephony.py), [ASR/LLM-адаптер](auditor/ai.py) и правила анализа. Провайдер телефонии в задании не указан, поэтому реализована граница интеграции: JSON с метаданными, явным ID сделки и расшифровкой. Для конкретной телефонии нужен адаптер её API, получающий метаданные и записи. Собственный локальный аудиофайл можно отправить в `whisper-1`: результат содержит текст и временные отметки без определения спикеров. Затем расшифровка приводится к формату импорта и связывается со сделкой. Опциональный анализ через OpenAI Responses API использует строгую JSON Schema: резюме, возражения, следующий шаг и подтверждающие цитаты. Код проверяет, что цитата действительно присутствует в указанном сегменте.

**Составитель отчёта** — [расчёты и правила](auditor/report.py). Python считает показатели и нарушения задач; анализ звонков добавляет договорённости и подтверждения. Система возвращает JSON и показывает результат в веб-интерфейсе. Создание и закрытие сделок, а также звонки учитываются за выбранные 30 дней; открытая воронка и проблемы задач — текущий срез всех открытых сделок, включая более старые. Сумма успешных сделок — бюджеты CRM, не денежные поступления.

[SQLite](auditor/store.py) хранит снимки CRM, импортированные расшифровки, анализ и отчёты в `runtime/auditor.sqlite3`. Аудио остаётся отдельными локальными файлами пользователя; результаты CLI также можно сохранить в JSON. Демонстрационный набор синтетический: без ключей используются локальные правила, внешний AI не вызывается. Подробная схема — в [docs/architecture.md](docs/architecture.md).

## 2. Что выполняется автоматически, что решает человек и три главных риска

**Система сама** читает и нормализует данные, рассчитывает показатели, находит сделки без незавершённых задач и с просрочками, извлекает сведения из расшифровок и формирует отчёт с рекомендациями и подтверждениями. Подключение внешних API и AI запускается явно соответствующими командами.

**Человек** проверяет спорные фрагменты и причины проблем, утверждает следующие действия, изменения в CRM и контакты с клиентами. Текущий проект работает на чтение: он выдаёт рекомендации, а руководитель выполняет утверждённые действия в своих рабочих системах.

1. **Неполнота и неверная связь данных.** Права токена ограничивают выгрузку; задачи контакта могут не относиться к конкретной сделке, а один клиент может вести несколько сделок. Нужны проверка покрытия источников, явные связи звонков со сделками и предупреждения о неполных данных.
2. **Ошибки распознавания и интерпретации.** Шум и неоднозначные договорённости могут привести к неверному выводу ASR, LLM или правил. В отчёте нужны цитаты, временные отметки и проверка руководителя; совпадение задачи с обещанием по ключевому слову остаётся предположением для проверки.
3. **Доступ к записям, коммерческим данным и токенам.** Требуются ограниченный доступ, подходящее хранение и согласованные условия обработки у внешних сервисов. Ключи передаются через серверное окружение, реальные данные остаются вне публичной папки `dist/` и Git.

## 3. Python: сделки без задач или с просроченными задачами

Самостоятельный пример — [examples/amocrm_problem_deals.py](examples/amocrm_problem_deals.py), **50 строк**, только стандартная библиотека. Он получает все страницы сделок и незавершённых задач и исключает закрытые статусы 142/143. «Без задач» означает отсутствие незавершённых задач, прикреплённых непосредственно к сделке; задачи контактов не учитываются. Выбираются все открытые сделки, а не только созданные за последние 30 дней. Время проверки просрочек фиксируется перед выгрузкой.

Нужны переменные `AMO_SUBDOMAIN` и `AMO_ACCESS_TOKEN`. Ошибка запроса прерывает выполнение; перенаправления запрещены, чтобы Bearer-токен не ушёл на другой адрес.

```python
"""Open deals without unfinished direct tasks or with overdue tasks (stdlib)."""
import json
import os
import re
import time
from collections import defaultdict
from urllib.parse import urlencode
from urllib.request import HTTPRedirectHandler, Request, build_opener

subdomain = os.environ.get("AMO_SUBDOMAIN", "").strip().lower()
token = os.environ.get("AMO_ACCESS_TOKEN", "").strip()
if not re.fullmatch(r"[a-z0-9](?:[a-z0-9-]{0,61}[a-z0-9])?", subdomain) or not token:
    raise SystemExit("Set AMO_SUBDOMAIN (name only) and AMO_ACCESS_TOKEN")
base = f"https://{subdomain}.amocrm.ru/api/v4/"
as_of = int(time.time())

class NoRedirect(HTTPRedirectHandler):
    def redirect_request(self, *args):
        return None
def fetch_all(entity, filters=None):
    page, rows = 1, []
    while True:
        params = {"limit": 250, "page": page, "order[id]": "asc", **(filters or {})}
        request = Request(base + entity + "?" + urlencode(params), headers={
            "Authorization": f"Bearer {token}", "Accept": "application/hal+json"})
        with build_opener(NoRedirect()).open(request, timeout=30) as response:
            if response.status == 204:
                break
            payload = json.load(response)
        rows.extend(payload["_embedded"][entity])
        if not payload.get("_links", {}).get("next"):
            break
        page += 1
    return rows


tasks_by_lead = defaultdict(list)
for task in fetch_all("tasks", {"filter[entity_type]": "leads", "filter[is_completed]": 0}):
    if task["entity_type"] == "leads" and not task["is_completed"]:
        tasks_by_lead[task["entity_id"]].append(task)
problems = []
for lead in fetch_all("leads"):
    if lead["status_id"] in (142, 143):
        continue
    tasks = tasks_by_lead[lead["id"]]
    overdue = [t["id"] for t in tasks if t["complete_till"] < as_of]
    if not tasks or overdue:
        problems.append({"id": lead["id"], "name": lead["name"],
                         "no_task": not tasks, "overdue_task_ids": overdue})
print(json.dumps({"as_of": as_of, "deals": problems}, ensure_ascii=False, indent=2))
```

## Попробовать за минуту

Требуется Python 3.10 или новее. Для демо достаточно стандартной библиотеки: установка пакетов и API-ключи не нужны.

```bash
git clone https://github.com/jaFuart/sales-ai-auditor.git
cd sales-ai-auditor
python3 -m auditor build-demo
python3 -m auditor serve --port 8080
```

Откройте [localhost:8080](http://localhost:8080). Статическая версия в `dist/` работает на обычном веб-хостинге и получает готовые JSON-отчёты. Через Python-сервер интерфейс получает данные из `/api/report`.

В Windows после перехода в папку проекта:

```powershell
py -m auditor build-demo
py -m auditor serve --port 8080
```

Другие способы запуска:

```bash
# Отчёт без браузера
python3 -m auditor report --days 30 --output report.json

# Docker
docker compose up --build

# Проверка
python3 -m unittest discover -s tests -v
```

## Как устроен проект

```text
auditor/                 Python: данные, расчёты, SQLite, API и CLI
dist/                    Готовый интерфейс и публичные синтетические отчёты
examples/                Короткая интеграция amoCRM и формат импорта звонков
docs/                    Архитектура, ответы на задание, сценарий презентации
tests/                   Проверки расчётов, интеграции и API
runtime/                 Локальная база и результаты; не попадает в Git
```

Три роли: координатор задаёт период и собирает источники; аналитик звонков извлекает факты с подтверждениями; составитель отчёта объединяет факты с показателями, рассчитанными кодом. В демо эти роли выполняют локальные модули. LLM нужен для анализа текста, а суммы и просрочки рассчитываются обычным Python.

Система предлагает действия. Руководитель проверяет спорные выводы и принимает решения; изменений в CRM, отправки сообщений и автоматической оценки сотрудников в этом проекте нет.

GitHub Actions проверяет проект при push и pull request. В репозитории также есть вручную запускаемый [workflow GitHub Pages](.github/workflows/pages.yml): он публикует только синтетическую папку `dist/`, если Pages настроен на GitHub Actions. Локальные реальные отчёты и ключи не предназначены для публичного хостинга.

### Что означает отчёт

| Показатель | Правило |
| --- | --- |
| Новые сделки | Созданы внутри выбранного периода |
| Успешные сделки и их сумма | Закрыты успешно внутри периода; сумма бюджетов в CRM |
| Доля успешных закрытий | Успешные / все закрытые внутри периода |
| Звонки | Произошли внутри периода |
| Открытая воронка и проблемы задач | Текущий срез всех открытых сделок, включая созданные раньше периода |
| Без задач | Нет незавершённых задач, прикреплённых непосредственно к сделке |
| Просрочка | Есть незавершённая задача со сроком раньше времени среза |

Сумма успешных сделок не равна полученным платежам. Задачи контакта не приписываются автоматически всем его сделкам. Несовпадение обещания в звонке с задачами — повод для проверки, а не доказательство нарушения.

Демо фиксирует время на **14 октября 2026 года, 18:00 МСК**, поэтому результаты воспроизводимы. События считаются в интервале `[начало, конец)`. История переходов по этапам в этот MVP не входит: график отражает события создания и закрытия, а воронка — текущие статусы.

### Подключить реальные данные

Передайте конфигурацию через переменные окружения. [.env.example](.env.example) перечисляет поддерживаемые параметры; файл `.env` автоматически не загружается. Токены используются только серверными командами.

```bash
export AMO_SUBDOMAIN=your-account
read -rsp 'amoCRM access token: ' AMO_ACCESS_TOKEN
export AMO_ACCESS_TOKEN
python3 -m auditor sync-amo
python3 -m auditor import-calls --input /path/to/calls.json
python3 -m auditor report --source live --days 30 --output runtime/report.json
python3 -m auditor serve --source live --port 8080
```

amoCRM-коннектор читает сделки, задачи, пользователей и воронки; проходит страницы и обрабатывает временные ошибки API. Начальная выдача и обновление OAuth-токенов выполняются вне демо. Данные сохраняются в `runtime/auditor.sqlite3`. Получение коллекций описано в документации [сделок](https://www.amocrm.ru/developers/content/crm_platform/leads-api) и [задач](https://www.amocrm.ru/developers/content/crm_platform/tasks-api), а авторизация — в [OAuth amoCRM](https://www.amocrm.ru/developers/content/oauth/step-by-step).

Короткий самостоятельный пример поиска проблемных сделок — [examples/amocrm_problem_deals.py](examples/amocrm_problem_deals.py), не более 50 строк. Ошибка доступа или запроса останавливает его: неполная выгрузка не выдаётся за полный отчёт.

Телефония подключается через нормализованный JSON-импорт; пример формата — [examples/calls.json](examples/calls.json). В примере вымышленные ID: перед импортом замените `deal_id` на существующую сделку, `manager_id` на её ответственного, а сам текст и время — на собственные данные. Готового подключения к конкретному провайдеру телефонии нет. Синтетические расшифровки демо не сопровождаются записями разговоров.

Для собственных аудиофайлов и расшифровок предусмотрены явные команды с OpenAI API:

```bash
read -rsp 'OpenAI API key: ' OPENAI_API_KEY
export OPENAI_API_KEY
python3 -m auditor transcribe --audio /path/to/call.mp3 --output runtime/transcript.json
python3 -m auditor analyze-calls --source live
```

Транскрипцию нужно привести к формату импорта и связать со сделкой. Команда анализа обрабатывает уже импортированные расшифровки. Сетевые операции требуют действительных ключей и отдельно оплачиваются у провайдеров. Без ключей доступен весь демонстрационный интерфейс.
